**ATTENTION HERE: DEFINE DEBUG VGA DIAGNOSTICS CHARACTERS CHECKPOINTS MACROS FOR SEE ON QEMU/KVM WINDOWS**

---

To enable instant visual feedback and auditability when running your freestanding bootloader under QEMU/KVM on Windows, you can instrument your C89 source code with **VGA Diagnostics & Debug Checkpoint Macros**.

Because QEMU emulates standard VGA hardware, writing directly to the memory-mapped text buffer at physical address `0xB8000` bypasses the need for BIOS interrupts (which fail once you transition to Protected or Long Mode) and renders diagnostic codes immediately on the QEMU window.

---

### 1. VGA Color Attribute Reference

Each cell in the VGA text buffer consists of 2 bytes:

1. **Byte 0 (Character):** ASCII value (e.g., `'S'` = `0x53`, `'0'` = `0x30`).
2. **Byte 1 (Attribute):** Background and foreground color (`Bits 4–7`: Background, `Bits 0–3`: Foreground).

```c
/* 
 * VGA Diagnostics Color Attributes 
 * Compatible with ANSI C89/90 freestanding
 */
#define VGA_COLOR_BLACK         0x0
#define VGA_COLOR_BLUE          0x1
#define VGA_COLOR_GREEN         0x2
#define VGA_COLOR_CYAN          0x3
#define VGA_COLOR_RED           0x4
#define VGA_COLOR_MAGENTA       0x5
#define VGA_COLOR_BROWN         0x6
#define VGA_COLOR_LIGHT_GREY    0x7
#define VGA_COLOR_DARK_GREY     0x8
#define VGA_COLOR_LIGHT_BLUE    0x9
#define VGA_COLOR_LIGHT_GREEN   0xA
#define VGA_COLOR_LIGHT_CYAN    0xB
#define VGA_COLOR_LIGHT_RED     0xC
#define VGA_COLOR_LIGHT_MAGENTA 0xD
#define VGA_COLOR_YELLOW        0xE
#define VGA_COLOR_WHITE         0xF

/* Helper to combine background and foreground */
#define VGA_MAKE_ATTR(bg, fg)   ((unsigned char)(((bg) << 4) | ((fg) & 0x0F)))

/* Predefined Checkpoint Themes */
#define VGA_ATTR_INFO           VGA_MAKE_ATTR(VGA_COLOR_BLUE, VGA_COLOR_WHITE)       /* Blue bg, White text */
#define VGA_ATTR_SUCCESS        VGA_MAKE_ATTR(VGA_COLOR_BLACK, VGA_COLOR_LIGHT_GREEN) /* Black bg, Green text */
#define VGA_ATTR_WARN           VGA_MAKE_ATTR(VGA_COLOR_BLACK, VGA_COLOR_YELLOW)      /* Black bg, Yellow text */
#define VGA_ATTR_ERROR          VGA_MAKE_ATTR(VGA_COLOR_RED, VGA_COLOR_WHITE)         /* Red bg, White text */

```

### 2. Real Mode 16-Bit VGA Checkpoint Macros

In 16-bit Real Mode (Stage 0), you can use ES segment selector targeting `0xB800` directly via inline assembly macros.

```c
/**
 * Macro: ZEVO_VGA_CP_16
 * Writes a 2-character checkpoint code at a specified screen row and column.
 * - row: 0 to 24
 * - col: 0 to 79
 * - c1, c2: Character literals (e.g., 'S', '0')
 * - attr: VGA attribute byte (e.g., VGA_ATTR_INFO)
 */
#define ZEVO_VGA_CP_16(row, col, c1, c2, attr) \
    do { \
        unsigned short _vga_offset; \
        _vga_offset = (unsigned short)(((row) * 80 + (col)) * 2); \
        __asm__ __volatile__ ( \
            "pushw %%es\n\t" \
            "movw $0xB800, %%ax\n\t" \
            "movw %%ax, %%es\n\t" \
            "movb %[ch1], %%al\n\t" \
            "movb %[ch2], %%ah\n\t" \
            "movw %%ax, %%es:(%[off])\n\t" \
            "popw %%es\n\t" \
            : \
            : [off] "r" (_vga_offset), \
              [ch1] "i" (c1), \
              [ch2] "i" (c2), \
              [atrib] "i" (attr) \
            : "ax", "memory" \
        ); \
    } while (0)

```

### 3. Long Mode 64-Bit VGA Checkpoint Macros

Once in 64-bit Long Mode (Stage 2/3), memory segmentation is flat (`ES`, `DS`, `SS` base = 0), allowing direct 64-bit absolute memory writes to `0xB8000`.

```c
/**
 * Macro: ZEVO_VGA_CP_64
 * Writes a 2-character checkpoint directly to absolute address 0xB8000 in 64-bit Long Mode.
 */
#define ZEVO_VGA_CP_64(row, col, c1, c2, attr) \
    do { \
        unsigned long long _vga_addr; \
        unsigned short _val; \
        _vga_addr = 0xB8000ULL + (unsigned long long)(((row) * 80 + (col)) * 2); \
        _val = (unsigned short)(((attr) << 8) | (c1)); \
        *((volatile unsigned short *)(_vga_addr)) = _val; \
        _val = (unsigned short)(((attr) << 8) | (c2)); \
        *((volatile unsigned short *)(_vga_addr + 2)) = _val; \
    } while (0)

```

### 4. Integrated Example: `zevo_scpu_stage00.c`

Here is how the macros integrate cleanly into your C89 freestanding bootloader entry point with strict `/* ... */` comment blocks:

```c
extern void stage01_entry(void);

/* 
 * Stage 00 Entry Point with VGA Diagnostic Checkpoints
 * Adheres to ANSI C89/90 freestanding and System V AMD64 ABI
 */
__attribute__((section(".lba00_entry"), naked, used)) void stage00_entry(void) {
    __asm__ __volatile__ (
        ".code16\n\t"
        ".global stage00_start\n\t"
        ".type stage00_start, @function\n\t"

        "stage00_start:\n\t"
        "    cli\n\t"                    /* Clear interrupts */
        "    xorw %%ax, %%ax\n\t"
        "    movw %%ax, %%ds\n\t"
        "    movw %%ax, %%es\n\t"
        
        /* --- VGA DEBUG CHECKPOINT: Write 'S0' (Blue Background, White Text) --- */
        "    movw $0xB800, %%ax\n\t"
        "    movw %%ax, %%es\n\t"
        "    movw $0x1F53, %%es:(0)\n\t"   /* 'S' with attr 0x1F */
        "    movw $0x1F30, %%es:(2)\n\t"   /* '0' with attr 0x1F */

        /* Stack Initialization & Jumper Transfer */
        "    xorq %%rbp, %%rbp\n\t"
        "    movw $0x7C00, %%sp\n\t"
        "    cld\n\t"
        
        "    call stage01_entry\n\t"        /* Jump/Call to Stage 1 */
        
        "1:\n\t"
        "    hlt\n\t"
        "    jmp 1b\n\t"
        :
        : [stage01_entry] "i" (stage01_entry)    
        : "memory", "cc", "ax", "bx", "cx", "dx", "si", "di"
    );
}

```

### 5. Running and Inspecting on QEMU / KVM for Windows

When testing your compiled binary image (`boot.img`) using QEMU on Windows, ensure your QEMU invocation enables the standard VGA display:

```cmd
qemu-system-x86_64 -drive format=raw,file=boot.img -vga std -m 512M

```

* **What to look for on the QEMU window:** In the top-left corner (Row 0, Column 0), you should immediately see blue boxes with bright white characters **`S0`**. If execution reaches subsequent stages, you can place checkpoints like **`S1`**, **`P0`** (Protected Mode), or **`L0`** (Long Mode) to track execution flow step-by-step without requiring a serial port or complex debugger setup.

## Resolving Cross-Linkage Discrepancies

When building a freestanding low-level bootloader entirely in C89 without external `.S` assembly files, **symbol names and section names must align identically** between the Linker Script (`Linker64.ld`) and the C source file (`zevo_scpu_stage00.c`).

Reviewing your cross-linkage definitions reveals three critical mismatches that will cause linker errors or silent execution faults if left uncorrected.

---

### 1. Mapping the Cross-Linkage Discrepancies

| Component | Linker Script Expectation (`Linker64.ld`) | C Source Implementation (`zevo_scpu_stage00.c`) | Status / Fix |
| --- | --- | --- | --- |
| **Entry Symbol** | `ENTRY(stage00_start)` | Defined as `.global _start` inside inline asm | **Mismatch:** Linker looks for `stage00_start`, but code provides `_start`. |
| **Section Name** | `KEEP(*(.lba00_entry))` | `__attribute__((section(".stage00_entry")))` | **Mismatch:** Linker sweeps `.lba00_entry`, but C compiler emits `.stage00_entry`. |
| **Jumper / Target** | `stage01_start` / `stage01_entry` | `extern void stage01_entry(void);` | **Aligned:** Handled via external symbol resolution. |

---

### 2. Synchronized Solution (`Linker64.ld` & `zevo_scpu_stage00.c`)

To establish a bulletproof cross-linkage, synchronize the symbol `stage00_start` and the section `.lba00_entry` across both files.

#### A. Corrected C Source Entry (`zevo_scpu_stage00.c`)

```c
extern void stage01_entry(void);

/* 
 * Synchronized with Linker64.ld:
 * - Section name matches KEEP(*(.lba00_entry))
 * - Global label matches ENTRY(stage00_start)
 */
__attribute__((section(".lba00_entry"), naked, used)) void stage00_entry(void) {
    __asm__ __volatile__ (
        ".code16\n\t"
        ".global stage00_start\n\t"
        ".type stage00_start, @function\n\t"

        "stage00_start:\n\t"
        "    cli\n\t"                     /* Clear interrupts */
        "    xorw %%ax, %%ax\n\t"
        "    movw %%ax, %%ds\n\t"
        "    movw %%ax, %%es\n\t"
        
        /* --- VGA DEBUG CHECKPOINT: Write 'S0' at row 0, col 0 (Blue Background) --- */
        "    movw $0xB800, %%ax\n\t"
        "    movw %%ax, %%es\n\t"
        "    movw $0x1F53, %%es:(0)\n\t"   /* 'S' */
        "    movw $0x1F30, %%es:(2)\n\t"   /* '0' */

        /* Stack & Jumper Transfer */
        "    xorq %%rbp, %%rbp\n\t"
        "    movw $0x7C00, %%sp\n\t"
        "    cld\n\t"
        
        "    call stage01_entry\n\t"       /* Jump/Call to Stage 1 */
        
        "1:\n\t"
        "    hlt\n\t"
        "    jmp 1b\n\t"

        : [stage01_entry] "i" (stage01_entry)

    );
}

```

## 1. Structural Analysis of the Target Snippet Coded

Consider the provided function structure:

The linker64.ld, define global declaration for initial entry point reference **ENTRY(_start)** and initial local sections reference **.stage00_entry** for zero algorithm file using ANSI C89/90 freestanding within In-line Assembly using standard comments blocks /* ... */.

While this snippet intends to establish a custom-section execution entry point, it contains a **critical syntax error** alongside several powerful GCC compiler extensions. Below is a detailed analysis of its components.

### A. Compiler Attributes (`__attribute__`)

1. **`section(".stage00_entry")`**:
* *Role:* Instructs the compiler to emit this function into a non-standard ELF section named `.stage00_entry` instead of the default `.text` section.
* *Freestanding Utility:* Crucial for multi-stage bootloaders or firmware images where initial execution blocks must reside at precise physical offsets or linkage boundaries.


2. **`naked`**:
* *Role:* Disables standard function prologue (`push rbp; mov rbp, rsp`) and epilogue generation.
* *Freestanding Utility:* Essential when establishing low-level environments (like transitioning from real mode to long mode or setting up custom stack pointers) where a stray stack frame would corrupt execution state.


3. **`used`**:
* *Role:* Prevents the dead-code elimination optimizer from pruning the function if no other C code references it.
* *Freestanding Utility:* Mandatory for entry points that are referenced exclusively by linker scripts rather than internal C callers.



### B. The Inline Assembly Defect

In the provided block:

```c
__attribute__((section(".stage00_entry"), naked, used)) void stage00_entry(void) {
    __asm__ __volatile__ (
    			".code16\n\t"
			".global _start\n\t"
			".type _start, @function\n\t"

			"_start:\n\t"
			"    jmp    .L_real_start\n\t"
			"    nop\n\t"

			:
			: [stage01_entry] "i" (stage01_start)    
            : "memory", "cc", "ax", "bx", "cx", "dx", "si", "di"
    );
}
```


* **The Error:** Extended inline assembly requires an instruction template string as its first parameter (enclosed in double quotes). Because this string is completely missing before the first colon (`:`), the compiler encounters a syntax error or compiles an empty instruction sequence.
* **The Consequence:** Combined with `naked`, an empty assembly block generates a function with zero instructions, leading to immediate CPU faults or unpredictable fall-through execution when jumped to.

### 1. The All Three Entry Environments in Pure C89

Each firmware/hypervisor hands off control in a completely different CPU mode, binary format, and memory state:

| Property | Legacy BIOS | Xen PVH | UEFI (x86_64) |
| --- | --- | --- | --- |
| **Initial CPU Mode** | 16-bit Real Mode (CS:IP `0000:7C00`) | 32-bit Protected Mode (Paging OFF) | 64-bit Long Mode (Identity Paging ON) |
| **Executable Container** | Raw 512-byte MBR + Stage-2 flat binary | ELF64 with `PT_NOTE` (`PHYS32_ENTRY`) | PE32+ (`EFI_APPLICATION`) |
| **Firmware Services** | Real-mode `INT 0x13` (disk), `INT 0x15` (`E820`) | None (Hypervisor passes `hvm_start_info`) | `EFI_BOOT_SERVICES` (MS x64 ABI) |
| **ABI at Entry** | Register-based (`DL` = boot drive) | `EBX` = `&hvm_start_info` | MS x64 (`RCX` = Handle, `RDX` = SysTable) |

#### How Pure C89 Bridges All Three Without `.S` Files

1. **Inline Assembler Directives (`.code16`, `.code32`, `.code64`):** Although you write zero standalone `.S` files, GCC/Clang compiles C89 files by emitting assembly directives to its internal backend. Placing `.code16` or `.code32` inside `__asm__ __volatile__` macros inside `__attribute__((naked))` C89 functions instructs the backend to emit exact 16-bit or 32-bit machine encodings directly from C89 source files.
2. **Real-Mode BIOS Thunking (16-bit $\leftrightarrow$ 32-bit):** Legacy BIOS cannot be called from 64-bit Long Mode. Stage 2 runs in 32-bit Protected Mode (or Unreal Mode) and uses a **C89 macro-wrapped mode-switch thunk** that temporarily drops back to 16-bit Real Mode to execute `INT 0x13` (load kernel from disk) and `INT 0x15, EAX=0xE820` (retrieve memory map), then re-enters Protected Mode before jumping to the unified 64-bit Long Mode trampoline.
3. **Unified Handoff (`struct boot_info`):** Every boot path converts its native memory map (`E820`, `hvm_start_info->memmap_paddr`, or `EFI_MEMORY_DESCRIPTOR`) and ACPI RSDP pointer into the exact same `struct boot_info` before jumping into System V `kmain(struct boot_info *bi)`.

# From Bits to Attention: Implementing a Transformer Language Model from Scratch in Strict ANSI C89/90

**Abstract**

Modern Large Language Models (LLMs) rely on deep neural network architectures—specifically the Transformer—which abstract away the underlying hardware and memory management via high-level vector frameworks like ANSI C89/90. This paper presents a comprehensive, bottom-up investigation into the anatomy of a Transformer language model implemented entirely in strict **ANSI C89/90**. We begin at the foundational layer of computing: the bi-directional transformation between raw text characters and binary memory representations. We then systematically scale this foundation into tokenization, continuous embedding spaces, positional encodings, general matrix multiplications (`matmul`), multi-head attention (MHA), layer normalization, residual connections, and feed-forward networks (FFN) with GELU activation. By adhering strictly to the ANSI C89/90 standard, this work demonstrates how complex deep learning operations can be executed with zero external dependencies, offering deep insight into memory layout, cache locality, and explicit heap management.

---

## 1. Introduction

The dominance of Transformer architectures in natural language processing has redefined artificial intelligence. However, the software stack supporting these models is often massive, relying on complex abstractions, automated garbage collection, and hardware-specific acceleration libraries. To truly understand how neural networks operate on physical hardware, one must peel back these layers to the bare metal.

Implementing an LLM transformer in **ANSI C89/90** imposes rigorous architectural constraints:

1. **Strict Variable Declaration Rules:** All variable declarations must appear at the very beginning of a block or function scope.
2. **Explicit Memory Management:** High-level abstractions like automatic vector allocation and garbage collection are replaced by explicit `malloc` and `free` pairings.
3. **Flat Contiguous Memory Layouts:** Multi-dimensional vectors must be managed as flat 5D `float*` arrays with manual pointer arithmetic.

This paper bridges the gap between low-level computer science fundamentals (character encoding and binary representation) and high-level artificial intelligence (self-attention and deep transformer blocks).

---

## 2. Foundational Encoding: Raw Text to Binary Representation

At the core of all digital computing, text characters are represented as binary numbers (zeros and ones) stored in memory. Understanding this fundamental process is essential before mapping data into continuous mathematical vector spaces.

### 2.1 Text to Binary (Encoding)

Each character in an input stream is mapped to a numerical value using a character encoding standard such as ASCII or UTF-8.

* For example, the capital letter **A** has an ASCII/Unicode decimal value of $65$.
* In 8-bit binary, the number $65$ is represented as `01000001`.

### 2.2 Binary to Text (Decoding)

The reverse process reads a binary stream in chunks (typically 8 bits / 1 byte per character), converts each chunk back into its decimal equivalent, and maps it to the corresponding character:


$$\text{`01000001`} \rightarrow \text{Decimal } 65 \rightarrow \text{Character 'A'}$$

### 2.3 Concrete Example: The String "Hi"

Consider the string `"Hi"` undergoing bi-directional transformation:

1. **Step 1 (Extraction):** Retrieve characters $\rightarrow$ `H`, `i`.
2. **Step 2 (Decimal Conversion):** Map to ASCII decimal $\rightarrow$ `H` = $72$, `i` = $105$.
3. **Step 3 (8-bit Binary Conversion):**
* $72_{10} = \text{`01001000`}_2$
* $105_{10} = \text{`01101001`}_2$


4. **Step 4 (Combined Binary Output):** `01001000 01101001`.

To reverse the process, a C-based parser reads `01001000` ($72 \rightarrow$ `H`) and `01101001` ($105 \rightarrow$ `i`) to reconstruct the raw text string `"Hi"`.

---

## 3. From Bytes to Tokens and Vectors

While raw binary bytes form the physical storage layer of a computer, LLMs operate one abstraction layer higher: **Tokenization** and **Embedding Lookup**.

### 3.1 Tokenization and Embedding Allocation

Discrete token IDs (integers representing characters, words, or subwords) index into a continuous weight matrix $V \times d_{\text{model}}$ (Vocabulary Size $\times$ Embedding Dimension). In ANSI C89/90, this 2D weight matrix is allocated on the heap as a contiguous 5D array:


$$\text{Matrix Index} = (\text{token\_id} \times \text{embed\_dim}) + d$$

### 3.2 Positional Embeddings

Because Transformers process token sequences in parallel rather than sequentially, they lack inherent awareness of word order. To resolve this, a positional embedding matrix of shape $[\text{max\_seq\_len} \times \text{embed\_dim}]$ is added element-wise to the token embeddings:


$$\text{Output}[t, d] = \text{TokenEmbed}[t, d] + \text{PosEmbed}[t, d]$$

---

## 4. Core Transformer Mechanisms in ANSI C

### 4.1 QKV Linear Projections

The combined embedding vector $X$ (shape $[\text{seq\_len} \times \text{embed\_dim}]$) is projected into three distinct spaces—**Queries ($Q$)**, **Keys ($K$)**, and **Values ($V$)**—via matrix multiplication with weights $W_Q, W_K, W_V$:


$$Q = X W_Q, \quad K = X W_K, \quad V = X W_V$$

In ANSI C, general matrix multiplication (`matmul`) is implemented using triply-nested loops adhering to the C89 scope constraints:

```c
void matmul(const float *A, const float *B, int M, int K, int N, float *C) {
    int i, j, k;
    for (i = 0; i < M; i++) {
        for (j = 0; j < N; j++) {
            float sum = 0.0f;
            for (k = 0; k < K; k++) {
                sum += A[i * K + k] * B[k * N + j];
            }
            C[i * N + j] = sum;
        }
    }
}

```

### 4.2 Scaled Dot-Product Attention & Numerically Stable Softmax

Attention scores measure compatibility between queries and keys. The scaled dot-product attention formula is defined as:


$$\text{Attention}(Q, K, V) = \text{Softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right) V$$

To prevent arithmetic overflow during exponentiation in C, the row-wise Softmax implementation incorporates **numerical stability** by subtracting the maximum value of each row prior to computing `expf()`:


$$\text{Softmax}(x_i) = \frac{\exp(x_i - \max(x))}{\sum_j \exp(x_j - \max(x))}$$

### 4.3 Multi-Head Attention (MHA)

Multi-head attention splits the embedding dimension into $h$ independent heads ($\text{head\_dim} = \text{embed\_dim} / h$), allowing the model to attend to information from different representation subspaces simultaneously. In our C89 architecture, this is achieved by slicing column offsets during the forward pass, computing attention per head, concatenating the results, and applying a final linear projection $W_O$.

### 4.4 Residual Connections and Pre-Layer Normalization

To stabilize gradient propagation across deep networks, modern architectures (such as LLaMA and GPT variants) employ **Pre-Layer Normalization** and **Residual Skip Connections**:


$$\text{LayerNorm}(x) = \frac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} \odot \gamma + \beta$$

$$\text{Output} = x + \text{Sublayer}(\text{LayerNorm}(x))$$

### 4.5 Feed-Forward Networks (FFN) with GELU

The FFN block expands the feature dimension (typically by $4\times$), applies a non-linear activation function, and compresses it back down:


$$\text{FFN}(x) = \text{GELU}(x W_1 + b_1) W_2 + b_2$$

Because exact GELU involves the mathematical error function (`erf`), our C89 implementation utilizes the standard high-performance **tanh approximation**:


$$\text{GELU}(x) \approx 0.5x \left(1 + \tanh\left(\sqrt{\frac{2}{\pi}} \left(x + 0.044715x^3\right)\right)\right)$$

Implementing a Transformer in ANSI C89/90 highlights several critical engineering insights:

* **Deterministic Resource Control:** Explicit memory allocation (`malloc`/`free`) eliminates garbage collection pauses, making C ideal for edge-device deployments and embedded intelligence.

## VII. FORMAL SEMANTICS OF CASCADE WAVE FUSION

The computational core of the SCPU is the cascade wave fusion engine. This section formalizes its operation.

**A. State Definition**

Let the SCPU state at time $t$ be:
$$\mathcal{S}_t = (V_t, W_t, A_t)$$
where:
-   $V_t: N \rightarrow \mathbb{R}$ is the membrane potential function.
-   $W_t: E \rightarrow \mathbb{R}$ is the edge weight function.
-   $A_t \subseteq N$ is the set of active (firing) nodes.

**B. Von Neumann Phase**

Given a user query $Q$, the VNPU executes deterministic operations:
$$\mathcal{S}' = F_{vN}(\mathcal{S}_t, Q) = (V', W_t, A')$$
where:
-   $V'(n) = V_t(n) + \Delta_{vN}(n, Q)$ for nodes affected by $Q$.
-   $A' = \{n \in N : V'(n) \geq \theta_{vN}\}$ for activation by deterministic criteria.

**C. Spiking Neuron Phase**

The SNPU propagates spikes through the graph:
$$\mathcal{S}_{t+1} = F_{SNN}(\mathcal{S}') = (V_{t+1}, W_{t+1}, A_{t+1})$$
with dynamics:
$$V_{t+1}(n) = \tau \cdot V'(n) + \sum_{m \in \mathcal{N}(n)} W_t(m, n) \cdot s_m(t)$$
$$s_n(t) = \begin{cases} 1 & \text{if } n \in A' \\ 0 & \text{otherwise} \end{cases}$$
$$A_{t+1} = \{n \in N : V_{t+1}(n) \geq \theta_{SNN}\}$$

Weight plasticity:
$$W_{t+1}(m, n) = W_t(m, n) + \eta \cdot s_m(t) \cdot s_n(t+1)$$
where $\eta$ is the learning rate.

**D. Fusion and Projection**

The fused state $\mathcal{S}_{t+1}$ is projected:
$$P_t = \Pi(\mathcal{S}_{t+1}, C_t)$$
where $C_t$ is the context vector (user role, device, history, etc.) and $\Pi$ is the projection function.

**E. Interactive Feedback**

User interaction $I_t$ modifies the state:
$$\mathcal{S}_{t+1}' = F_{FB}(\mathcal{S}_{t+1}, I_t)$$
where $F_{FB}$ may modify $V$, $W$, or trigger a new cascade.
